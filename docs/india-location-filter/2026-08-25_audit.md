# India location filter — audit, 2026-08-25

## 2026-08-25 — re-audit against the live table, five weeks on

**Goal**: re-measure the filter now that it has shipped, against a freshly pulled
`data/lancedb` (317,421 rows — 1.86x the 170,480 of the 2026-07-20 inventory).

**Tool**: `scripts/eval/location_filter_audit.py`. It models `geo.where("india")` as Python
predicates over `lower(location)` rather than re-deriving the term list, so `geo.EXCLUDE`'s
NOT-LIKE guards and the `indiana` guard are honoured; `geo.REGIONS` is deliberately excluded
because its values are city *keys*, not alias substrings, and the india clause already iterates
every city. Verified two ways. On 12 trap strings including "Surat Thani, Thailand", "Indianapolis, IN",
"Kalyani Nagar, Pune" and the knowingly-accepted "Hyderabad, Pakistan" — and, decisively,
against the production clause itself: `t.count_rows(filter=geo.where("india"))` executed by
LanceDB returns **49,480**, and the audit's Python model returns **49,480**. The model is
measured equal to the filter, not argued equal to it.

*(Those two figures are the pre-ADR-0086 filter, which is what this section measured. After the
change both read **49,892** — the tool re-checks itself on every run and refuses to continue on
a mismatch, which is how it caught its own model going stale when `geo` grew three clauses.)*

### The method correction that mattered

The first version of this audit reported **100.00% recall — and it was a tautology, not a
result.** It judged the filter against a "wider net" of `india-word OR state-name`, but the
filter's own clause is `india-word OR every city OR state-name`, so the net was a strict
*subset* of the thing under test and the residue was zero by construction.

Recall therefore cannot be measured with any term drawn from the gazetteer. This pass uses
signals independent of the city map: the ISO alpha-3 `IND`, and workday's `City, ST, IN`
subdivision form. A bare trailing `, IN` is genuinely ambiguous — India's alpha-2 *and*
Indiana's USPS code — so it is reported as two halves rather than assigned to either country.

### Field health — the ceiling on recall that `geo` does not own

- **no `location` field at all (NULL): 8,592 (2.7%)**
- field present but empty: **0** — so every gap is a missing field, not a blank one
- a placeless string ("Remote", "N/A", "Remote job"): **6,474 (2.0%)**
- **unfilterable by any place filter: 15,066 (4.7%)**

("US"/"USA" were initially counted as placeless. They are not — they name a country and are
perfectly filterable — so they were removed; that is the 5.0% -> 4.7% difference.)

Concentrated in specific scrapers, so this is a scraper defect, not a gazetteer one:
zoho 17.3%, successfactors 14.8%, recruitee 13.4%, keka 8.6%, greenhouse 7.8%.

### Recall — 98.90%

The filter matches **49,480 rows (15.6% of the table)**, of which **20,217 (40.9%) carry no
"india" word at all** — the blind spot that justified the gazetteer, undiminished. Its
*share* fell (47% -> 40.9%) while its absolute size nearly doubled (11,764 -> 20,217),
so the gazetteer is carrying more rows than ever even as the naive filter closes a little
of the relative gap.

Misses, by signal confidence:

| signal | rows | distinct | reading |
|---|---|---|---|
| `IND` alpha-3 | 336 | 27 | India (`IND-BLR-Divyasree Technopolis`, `IND BNGL FL2-3 TWR 3`) — but see below: the `\bind\b` probe is looser than the shipped clause and ≥3 of these are not India |
| `City, ST, IN` | 102 | 26 | unambiguous India (`Jagiroad, AS, IN`, `Vemagal, KA, IN`, `Remote, KA, IN`) |
| trailing `, IN` → India | 113 | 53 | `Chakan`, `CHEYYAR CC`, `Singahalli`, `Ambala` |
| trailing `, IN` → Indiana | 226 | 45 | correctly NOT matched — `Indianapolis, IN`, `Fort Wayne, IN` |

**438 misses on these probes** — a figure since retired: the probes are now inside the filter,
and the `\bind\b` one admits `Grayslake, Ind` (Illinois) and `King Street Ind Estate` (UK), so it
is a list to read rather than a total. Plus **339 rows that cannot be resolved from the string alone**
(a trailing ", IN" is India's alpha-2 *and* Indiana's USPS code).

That gives a recall **upper bound of 99.12%** — and it is a bound, not a measurement. The
numerator counts every matched row including the false positives below, and the denominator's
miss term is only what these probes can *see*: an India row written as a bare tail town with no
country marker is invisible to the filter and to the probe alike, so it can never enter the
denominator. Only the by-hand read below bounds that residue.

Reading the top 110 unmatched strings by hand found **no Indian city at the head** — the
residue is entirely US/EU/APAC. The misses are tail towns reachable only via a country marker:
Jagiroad, Chakan, Cheyyar, Vemagal, Hindupur, Singahalli, Jamnagar, Kurnool, Kanchipuram,
Alwar, Ambala, Rourkela, Mehsana, Sri City.

A scan for ~90 Indian cities absent from `geo.CITIES` **independently re-confirmed the existing
exclusions**: the three loudest hits were all traps, not misses — `salem` 245 (Jerusalem,
Winston-Salem), `kota` 162 (**Dakota**), `agra` 30 (Agrate Brianza, Italy). Do not add these.
`erode` (Wernigerode) is the same class and should not be added either.

### Precision — one real defect, small blast radius

**The country clause is a substring**: `LIKE '%india%' AND NOT LIKE '%indiana%'` matches
**"Indian Head, MD"**, "Indialantic, FL", "Indian Springs, NV", "Indianola, PA" and Diego
Garcia's "British Indian Ocean Territory". **19 rows, 11 distinct strings**, of which 2 are
genuinely India — so ~17 true false positives, 0.03% of matches.

Worth noting the substring form is not simply wrong: `IN_India_WFH` has no word boundary around
"india" and a `\bindia\b` test would *miss* it. A fix should exclude the known non-India
"Indian *" places, not switch wholesale to a word-boundary match.

18,065 rows rest on a city alias alone (no india word, no state name) — dominated by
bengaluru 7,264, pune 2,380, hyderabad 2,115, chennai 1,614. These are the design working as
intended, not suspects to remove; they are listed so the tail stays readable by hand.

### Not acted on

Diacritic folding would recover **0** rows: `geo.STATES` already hardcodes the observed variants
(`karnātaka`), so NFKD folding buys nothing today. Re-check if a new ATS lands.

### geo.py's knowingly-accepted collisions, finally counted

`geo.py` lists hyderabad (Pakistan), kochi (Japan), thane (Thanet UK) and madras (Madras, OR) as
"accepted as negligible for a tech-jobs corpus". Negligible is a quantity, so it is now measured
rather than asserted: **hyderabad x pakistan 1, kochi x japan 0, thane x thanet 0, madras x
oregon 0.** The single hit is `Hyderabad; Bangalore; Pakistan; India; Noida` — a multi-location
string that *is* India. **True cost today: 0 rows.** The judgement call was right.

## What was changed as a result (ADR-0086)

The audit above measured; this is what shipped off the back of it. Measured against the same
table, with the pre-change clause as the control:

| | rows |
|---|---|
| before | 49,480 |
| `IND` alpha-3, anchored + airport-guarded | +327 |
| `City, ST, IN` subdivision tail | +102 |
| `INDIA_EXCLUDE` closes the `%india%` bleed | −17 |
| **after** | **49,892  (+412, +0.83%)** |

All 46 distinct added strings were read by hand. 44 are unambiguously India; **two are not
verifiable from the string alone** — `Ind Area` (zoho) and `IND LBT` (workday/Lowe's) — and are
accepted rather than claimed. All 17 removed strings were read
by hand and are not. `Nagpur, Maharashtra, British Indian Ocean Territory` correctly survives via
`maharashtra`, because the new guards are scoped to the country sub-clause rather than the whole
expression.

Two traps were caught during implementation and would each have introduced a fresh false-positive
class:

- **`IND` is Indianapolis's IATA code.** `IND U; CVG SD; United States, PA, Philadelphia -
  Remote; MKE W; MSP` is a list of US airports.
- **`'% ind'` claims "Grayslake, Ind"** (Illinois). The shipped form is `'% - ind'`.

Verified after: 0 rows matched for Indianapolis, Indiana, Indianola, Grayslake or the airport
string. `tests/test_geo.py` fails 8-missed + 5-false-positive against the pre-fix clause and
passes clean after; full suite 1,572 passed.

**Not done, deliberately:** the hand-found tail towns (the subdivision rule already reaches most),
and the 339-row ambiguous trailing-", IN" bucket, which cannot be resolved from the location
string alone.
