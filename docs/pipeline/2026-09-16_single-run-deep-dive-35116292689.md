## 2. `scrape` — floor-bound exactly as the planner predicted

`scrape_plan`'s own advance diagnostics (before any shard ran) called this: *"the plan itself
predicts a floor-bound shard — one board at 28.0 min against a 16.0 min even share."* Actual
landed at shard 10, **2046 s (34.1 min), 98% one board**: `oracle:ejwl.fa.us2.oraclecloud.com`.
actual/predicted for that shard was **1.19×** — the floor materialized almost exactly where
forecast, just 19% heavier than sized. No packing change fixes this; per the skill's own
arithmetic, `wall = max(Σ/concurrency, slowest single item)` and this shard *is* that second term.

Two things about that board specifically:

- **It's a known, already-adjudicated bottleneck, reconfirmed real today.**
  `docs/oracle/2026-09-16_are-the-ejwl-and-jpmc-pods-real.md` (same date, written before this run)
  sampled 300 live titles and found `ejwl` is 0.0% test/demo-marked — ordinary hospitality
  postings, not synthetic data. The *cost* case is separate and still stands: Oracle's API serves
  no offset past 10,000, so this Board reads only 9,926 of its 13,642 postings every run (~27%
  permanently unreachable by construction), is permanently ADR-0053 scope-excluded (§5 confirms
  it again this run, 521 rows), and is the single most expensive Board in the pipeline. This run
  adds one more data point: **shard 10 also carried the highest 429/network retry ratio of any
  shard (0.30, vs 0.07–0.17 everywhere else, 2,307 rate-limit retries)** — the pod is throttling
  this board specifically, which is part of why it runs heavy even against its own floor estimate.
  This remains a coverage/value call to make deliberately, not a bug to fix.
- Shard 12 (`apple:jobs.apple.com`, 31.1 min, 98% floor) is the second floor-bound shard — expected
  and already documented as Apple's known single-board cost.
- Shard 11 was *not* floor-bound (53%) but had the run's highest actual/predicted ratio (1.43×,
  slowest board `jazzhr:amadaseniorcarenorthshore`) — not the critical-path owner, but the shard
  furthest off its own estimate for a non-floor reason; no obvious cause surfaced in its retry or
  error breakdown, worth a second look if it recurs.

**Error rate and egress were both clean:** 31 board errors across 20,000 attempted boards (0.2%),
no shard hit its time budget, and 0/15 shards showed WARP degrading to direct — no repeat of the
WARP-install failure chain from memory. Nothing here needs action.

## 4. GitHub-hosted runner behavior — the headline finding

**~16% of this run's entire wall clock (651 s of 68 min) was spent inside a single step —
`pip install "uv==$UV_VERSION"` — with no relationship to the amount of work each job actually
did.** This is not a one-off:

| job | this run's install time |
| --- | ---: |
| `join` | 16 s |
| `embed (4)` | **302 s** |
| `merge` | **349 s** |
| every other `embed` shard | 16–29 s |

`embed (4)`'s job total was 498 s — the run's flagged embed anomaly (2.07× the 241 s median,
`fanout_embed.py`'s own "no per-Doc floor, check before assuming a fluke" warning). Breaking it
down: the actual embedding step took a perfectly normal 182 s; **the pip-install step alone (302 s)
was the anomaly**, not the embedding work. `merge` — a single non-fanned-out job, so nothing
averages this away — drew the same fate: 349 s of its 13.4 min (44%) went to the identical step.

This is not specific to this run. Pulling the same step across the four prior successful runs
(`35108955671`, `35098924603`, `35093678492`, `35088621664`) shows **every single one** had at
least one `embed` shard spike well past baseline on this exact step, independent of shard index:

| run | worst embed-shard install time | 2nd worst |
| --- | ---: | ---: |
| 35108955671 | 562 s | 36 s |
| 35098924603 | 274 s | 256 s |
| 35093678492 | 168 s | 84 s |
| 35088621664 | 65 s | 28 s |
| **35116292689 (this run)** | **302 s** | (merge: 349 s) |

By contrast `scrape`'s install step (`pip install -e ".[scrape]"`, a local editable install, no
PyPI network fetch of the tool itself) never varies past 6–24 s across all 15 shards in this run.
The pattern points at PyPI-side or GitHub-runner-network variance specifically on resolving/
downloading the `uv` wheel — the fix earlier in the day (`2026-09-16_stage-timing-and-cut-
candidates.md`, ADR-0122's uv migration) addressed per-shard *setup* overhead broadly and measured
it solved (27 s total setup on that day's sampled straggler) — but that measurement predates this
run and evidently didn't catch this specific step's variance, since it's still costing minutes on
`merge` and `embed` five runs in a row. Worth its own look: pinning/caching the `uv` wheel (e.g.
`actions/cache` keyed on `UV_VERSION`, or switching to `astral-sh/setup-uv`, which fetches the
binary from GitHub releases rather than resolving through PyPI) would likely remove this
recurring, unforced cost — plausibly several minutes off `merge` alone on an unlucky run, since
`merge` has no fan-out to amortize it across.

Everything else about the runners was unremarkable: standard `ubuntu-latest`, no queueing, every
job well inside its `timeout-minutes` budget (68 min actual vs. up to 358 min worst-case summed
budget), `request-compaction` correctly skipped (conditional job, not an error).

## 5. `merge` — sync, scope exclusion, and one confirmed defect

**`update_meta`:** no derivations sweep (`v11` stored = `v11` in code); 400 rows queued to
re-derive is ordinary steady-state churn. Experience 5 gained/**34 lost**/32 retiered/18 moved;
salary 11 gained/**39 lost**/0 retiered/14 moved. Per ADR-0066, `lost` is the figure worth
watching and `retiered` is direction-blind — these magnitudes are consistent with background
churn on a non-sweep run, not evidence of a regression, but they're the numbers to keep an eye on
across runs.

**ADR-0053 scope exclusion:** 40 Boards, **2,772 eviction-candidate rows held out of scope**, no
drain (per the skill, this accretes forever and must be watched across runs, not within one). The
largest single pool is **not** the already-documented `ejwl` — it's
`successfactors:careers.hcltech.com` at **2,028 rows**, confirmed growing slowly against the prior
run (2,016 → 2,028, +12). This board has been the largest exclusion pool in both runs I checked
and, unlike `ejwl`, doesn't appear to have had the same root-cause investigation (is it a real
structural cap like Oracle's 10k offset, or something fixable?) written up anywhere in `docs/` or
`CLAUDE.md`. Worth the same treatment `ejwl` and `jpmc-test` just got.

**ADR-0083 grace period:** 1,187 ids unconfirmed this run; of 1,988 carried in from last run, only
75 reappeared (3.8%) and 422 are unconfirmed again. I don't have enough run history pulled to say
whether that reappearance rate is normal — flagging it as a number to baseline, not a verdict.

**Confirmed defect — `greenhouse:speechify` lost 720 rows with zero adds, no error, and no
scope-exclusion flag, while the live board is still full:**

- The merge log's eviction batches show `greenhouse:speechify` contributing 720 of the 812 net
  greenhouse evictions this run (via provider-name-boundary regex extraction, not a whitespace
  split — see the skill's caution on that trap) — **and zero adds**.
- Nothing else in the join or merge logs mentions `speechify` at all: no board error, no
  `mark_truncated`, no ADR-0053 exclusion line. The eviction went through the ordinary "confirmed
  absent on two consecutive scrapes" path (ADR-0083) with no signal that anything was wrong.
- The two preceding runs (`35108955671`, `35098924603`) show **zero** `speechify` add/evict
  activity — this board was completely stable immediately before this run's mass eviction.
- I live-checked the real endpoint just now: `boards-api.greenhouse.io/v1/boards/speechify/jobs`
  returns **HTTP 200, 361 currently-open jobs**.

Put together: the served index just evicted ~720 rows for a board that is demonstrably still live
and populated, and no existing pipeline signal caught it. This is the strongest concrete finding
in this run — worth a follow-up to determine whether the scrape for this board silently failed
(parsing break, pagination change, a slug/redirect issue) on the run(s) that fed its two
consecutive near-empty reads, since nothing here currently distinguishes that from a real mass
closure short of the live check just performed.

**`index prune`:** 0 rows evicted (0 off-Board, 0 duplicate) — clean, keep-set matched.
**`role_trends`:** 9,923 rows appended, non-tech share 25.8% (within ADR-0017's tolerated creep),
reassignments negligible (0.01% of rows). **Storage:** squashed successfully this run, live 6.71
GB — routine; the 80.42 GB "used" figure is pre-squash noise per the skill's own caution and isn't
a trend signal on its own.

## Summary — ranked
